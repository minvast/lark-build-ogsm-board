# Base 搭建安全与幂等守则

## 1. 固定目标和写入权限

- 多部门来源必须先确认 Base 拓扑；用户选择独立 Base 时，为每个部门创建独立表、视图、仪表盘和工作流。
- 为每个目标保存 `base_token`、`table_id`、规范记录数和源指纹。恢复中断任务时先读状态与在线对象，不得盲目重建。
- 明确“来源维护字段”和“人工维护字段”。默认只刷新 O/G/S/M、行动、截止日期及来源审计字段；保留人工维护的人员、状态、风险、下一步动作和证据。

## 2. 正确读取飞书记录列表

完整读回使用足够大的 limit，并确认 `has_more=false`。CLI 可能返回以下任一结构：

1. 对象列表：`data.items[]` 或 `data.records[]`，每条包含 `record_id` 与 `fields`。
2. 矩阵列表：`data.data[][]`、`data.fields[]`、`data.record_id_list[]`。按列名将每行还原为字段对象，并按相同下标绑定 record ID。

空对象列表不等于空表。如果响应包含非空 `data.data`，必须按矩阵解析。解析后同时核对返回行数、record ID 数、总数和分页标记。

## 3. 强制 upsert 顺序

1. 读取并验证规范数据：`源记录ID` 不为空且唯一。
2. 完整读取目标表，只投影 upsert 键和必要审计字段也可以，但不得遗漏分页。
3. 建立 `源记录ID -> record_id` 映射。目标表有空键或重复键时停止，不得创建记录。
4. 只对不存在的键创建；只对唯一匹配的键更新。单批不超过 200 条。
5. 写入后完整读回，核对总数、唯一键数和期望键集合。
6. 立即重复同一 upsert。验收条件为 `created=0` 且 `updated=规范记录数`，随后再次核对在线总数。

对飞书暂时性限流或冲突错误采用串行、有界退避重试。每次重试后仍需回读；不要并发补写，也不要因为响应超时就假设写入失败。

## 4. 重复记录处理

发现重复时先停止后续记录写入。把完整 `record-list` JSON 保存为审计输入，并运行：

```bash
python3 scripts/audit_base_records.py record-list.json \
  --expected-normalized normalized.json \
  --output audit.json \
  --cleanup-plan duplicate-cleanup-plan.json
```

只有以下条件全部满足时才能生成可执行清理计划：

- 已完整读取，`has_more=false`；
- 唯一源键集合与规范数据完全一致；
- 每个保留和删除目标都有明确 record ID；
- 没有计划外记录、空键或缺失的规范键。

向用户报告删除数量、保留规则和不可恢复性，并等待明确授权。授权后：

1. 重新读取在线记录；
2. 验证保留/删除 record ID 集合与批准计划完全一致；
3. 只删除计划中的 record ID；
4. 回读并确认删除 ID 全部消失、保留 ID 全部存在、总数和唯一键数符合预期；
5. 保存清理结果与时间。

不得按筛选条件宽泛删除，不得重新计算一份未经用户批准的新删除清单。

## 5. 对象级回读

- 字段：核对类型、选项、公式表达式和人员字段单双值。
- 视图：核对六个视图的类型、过滤条件和分组，不只核对名称。
- 仪表盘：逐组件读取数据，核对使用的维度和指标。
- 工作流：创建后立即关闭，并回读状态为 `disabled`；接收人必须引用真实人员字段或明确升级字段。
- 多 Base：每个 Base 单独产出验收文件；一个 Base 通过不代表另一个已通过。
